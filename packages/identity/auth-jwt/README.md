# @deepseek-ai/dsh-auth-jwt

English | [中文](README.zh.md)

JWT Authentication Provider that signs short-lived access JWTs and rotating refresh JWTs. It registers `bearer` evidence and the `jwt` credential lifecycle method on `ctx.auth`, while `ctx.authTokens` retains the authoritative server-side refresh-family state.

## Configuration

`issuer` and `audience` are exact JWT claim values. `accessTtlSeconds` defaults to 900 and is capped at 3,600; `refreshTtlSeconds` defaults to 2,592,000, is capped at 31,536,000, and must not be shorter than the access lifetime. `clockToleranceSeconds` defaults to zero and is capped at 300.

`keys` contains one to sixteen HS256 keys. Each entry has a protected-header `keyId` and a canonical base64url `secret` encoding 32-128 random bytes. `activeKeyId` selects the signing key. Verification accepts any configured key, so a deployment rotates keys by adding the new key, selecting it as active, retaining old keys until their tokens expire, and then removing them.

```yaml
- name: '@deepseek-ai/dsh-auth-jwt'
  config:
    issuer: https://auth.example.test
    audience: dsh-host
    activeKeyId: key-2026-08
    keys:
      - keyId: key-2026-08
        secret: BASE64URL_ENCODED_RANDOM_SECRET
```

## Credential Flow

After another Provider proves identity, call `ctx.auth.credentials.issue(authenticationMethod('jwt'), request)`. The result contains one `access` JWT and one `refresh` JWT. A trusted transport submits the access value as `{ kind: 'bearer', token }` to `ctx.auth.authenticate()` and submits the refresh value to `ctx.auth.credentials.refresh()`.

Both JWTs fix `alg`, `kid`, `iss`, `aud`, `typ`, `iat`, `nbf`, `exp`, and `jti`. `typ=access` and `typ=refresh` are not interchangeable. Access JWT verification also inspects the server-side family and, for a user principal, calls `ctx.users.requireActive()`. Disabling or deleting a user therefore rejects an otherwise cryptographically valid access JWT.

The refresh JWT carries the high-entropy opaque refresh secret generated by `ctx.authTokens`, plus its family and Credential ids. The durable Provider stores only the secret digest. Refresh first verifies the signed `typ=refresh` envelope, then gives the inner secret to `ctx.authTokens.rotate()`. One successful rotation consumes it; replay of the old refresh JWT atomically revokes the family, so signed JWTs cannot bypass server-side state.

Issue and refresh resolve the active decoded signing key before mutating family state. Both JWTs are signed through the `ctx.authTokens` transactional preparation callback while the durable Provider holds its mutation lock. The family creation or rotation commits only after both signatures succeed; a signing or candidate-consistency failure leaves no new family and does not consume the old refresh Credential.

## Inspection and Revocation

`ctx.auth.credentials.inspect(authenticationMethod('jwt'), request)` returns persistent refresh Credential metadata projected from `ctx.authTokens`. Self-contained access JWT ids are not persisted and therefore do not appear in inspection. Revoke accepts Credential, family, or principal targets through the same lifecycle runtime; family and principal revocation immediately invalidate matching access JWTs because every access verification checks current family state.

## Model Experience

### Authentication state

#### What the model sees

Nothing. `ctx.auth.authenticate()` keeps JWTs, claims, keys, family state, and authentication failures Host-only and registers no prompt section, tool, or session event.

#### Token effect

Zero. Authentication does not add, remove, or rewrite model-input tokens.

#### KV Cache effect

Independent. JWT issue, verification, refresh, and revocation do not change a model-visible request prefix.

## Known Limitations and Deferred Work

- **Symmetric keys** - this Provider fixes HS256 and requires every verifier to hold signing secrets; asymmetric or remote KMS signing requires another JWT Provider design.
- **No durable access-token index** - inspection and targeted revocation operate on refresh Credentials and families; access JWT verification uses expiry plus current family and user state.
- **Host-side key configuration** - key values are Loader configuration; a starter may later resolve secret references from `ctx.credentials` without changing JWT claim or family semantics.
