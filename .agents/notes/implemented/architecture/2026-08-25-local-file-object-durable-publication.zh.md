# Agent Note: 本地文件对象的持久发布

Status: implemented

[English](2026-08-25-local-file-object-durable-publication.md) | 中文

## 问题

不可变文件对象引用可能比创建它的进程存活更久。如果在文件字节和所有新目录项持久化之前返回，崩溃后可能出现数据库引用有效但对象已经消失的情况。并发发布者也需要一个无需进程内锁的禁止覆盖提交点。

## 决策

`@deepseek-ai/dsh-file-storage-local` 在显式配置的私有 root 下使用 SHA-256 内容寻址。写入会流式进入同一文件系统 staging 目录中的随机命名、仅所有者可访问文件，计算完整对象摘要和长度，刷新文件，再通过原子硬链接发布。`EEXIST` 表示另一个发布者已经成功；Provider 验证现有对象的元数据和字节后返回相同引用。

目录创建会从每个新 leaf 到最近的已知现有祖先建立持久化链。发布和去重都会刷新从摘要 bucket 到存储 root 的每一级目录。Windows 上 Node 无法打开目录句柄，因此跳过目录刷新，但文件刷新和原子硬链接发布仍然有效。

引用只暴露不透明相对内容 key。Provider 在解析路径前派生并交叉检查 backend、对象 id、key、摘要和字节长度。`open` 在调用方消费数据流时验证摘要和长度。取消不会等待仍阻塞在自身异步工作中的来源迭代器；Provider 会观察它最终的清理 rejection，但不会因此延迟 staging 清理。

## 备选方案

**使用 rename 发布。** rename 可以替换现有对象，因此需要额外锁才能保证不可变并发发布。创建硬链接本身提供一个原子且禁止覆盖的提交点。

**使用进程内发布锁。** 它不能协调多个进程，还会增加可变生命周期状态。内容寻址结合硬链接 `EEXIST` 可以跨进程工作。

**在引用中保存绝对路径。** 这会暴露部署布局，并阻止迁移已持久化的对象树。不透明相对 key 把物理 root 策略保留在 Provider 内部。

## 结果

相同字节无需注册表或锁服务即可去重，返回的引用在重启后仍可读取。读取需要消耗 CPU 重新计算 SHA-256，重复写入需要在返回前重读获胜对象，较晚的目录刷新失败还可能留下不可达的不可变对象。API 有意不提供删除操作；所有权、保留和垃圾回收仍由本 Provider 之外的组件负责。
